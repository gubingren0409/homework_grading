## 一、问题诊断

### 用户观察
> "我注意到之前运行实际样例测试的时候在各个阶段都有长尾的问题，后来我仔细想了想，api调用层模型有长尾就算了，本地的算法、代码执行层面有长尾是不正常的，所以很有可能会就是sqlite的写锁问题导致的"

**分析结论**: ✅ **诊断正确！**

### 根本原因

#### SQLite的写锁机制
```
即使使用WAL模式：
- ✅ 允许读写并发
- ❌ 写操作仍然完全串行（只能有1个写事务）
```

#### 当前配置（src/db/core_utils.py）
```python
_WRITE_LOCK_MAX_RETRIES: int = 6           # 最多重试6次
_WRITE_BACKOFF_BASE_SECONDS: float = 0.05  # 基础退避50ms
_WRITE_BACKOFF_MAX_SECONDS: float = 1.0    # 最大退避1秒
_SQLITE_BUSY_TIMEOUT_MS: int = 5000        # 忙等待5秒

PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA busy_timeout=5000;
```

#### 最坏情况延迟计算
```
5秒(busy_timeout) + 6次重试 × 1秒(max_backoff) = 11秒！
```

这完美解释了长尾延迟问题。

### 并发写入场景分析

#### 批量批改任务
```
100个学生 × 10个题目 = 1000次写入操作

每个任务的写操作：
- update_task_status() - 状态更新（至少3次）
- update_task_progress() - 进度更新（多次）
- touch_task_heartbeat() - 心跳更新（每30秒）
- save_grading_result() - 结果保存（每题1次）
- save_paper_grading_report() - 报告保存（1次）

估算：一个100学生批量任务 = 3000+次写操作
```

#### 问题
在SQLite下，这3000+次写操作**完全串行执行**，导致：
- 大量锁等待
- 重试机制放大延迟
- 长尾延迟高达11秒

## 二、PostgreSQL迁移方案

### 核心优势

#### MVCC（多版本并发控制）
```
PostgreSQL使用MVCC：
- ✅ 真正的并发写入
- ✅ 无写锁等待
- ✅ 读写不互相阻塞
- ✅ 支持数百个并发连接
```

### 预期改善

| 指标 | SQLite | PostgreSQL | 改善 |
|------|--------|-----------|------|
| 并发写入 | 串行（1个） | 并行（无限制） | ∞ |
| 写锁等待 | 最高11秒 | 无 | -100% |
| 批量吞吐 | 基准 | 5-10倍 | +500-1000% |
| 长尾延迟 | 11秒 | <100ms | -99% |

### 迁移工作量

#### 时间估算
- Phase 1: 准备工作（1天）
- Phase 2: 代码适配（2-3天）
- Phase 3: 测试验证（1-2天）
- Phase 4: 部署上线（1天）
- **总计**: 5-7天

#### 技术方案
1. **数据库适配层** - 抽象接口，支持SQLite和PostgreSQL
2. **Schema迁移** - AUTOINCREMENT → SERIAL
3. **数据迁移脚本** - 自动化迁移工具
4. **向后兼容** - 保留SQLite支持（可选）
